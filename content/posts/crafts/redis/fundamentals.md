# 一、Redis 基础与数据结构

## 1. 基础认识

### Redis 的定位与适用场景

Redis 是以内存为主要存储介质的键值数据库，支持字符串、集合、有序集合和消息流等数据结构。它常用于缓存、计数、排行榜、限流、分布式锁和轻量消息队列。

Redis 的优势是低延迟和丰富的原子操作，但内存成本高，持久化与事务能力也不能直接替代关系型数据库。核心业务数据通常仍以数据库为准，Redis 更适合作为访问加速层或特定数据结构的计算工具。

### Redis 的高性能来源

Redis 快主要有四个原因：数据主要在内存中操作；命令执行路径短；常用数据结构经过专门优化；网络层使用 I/O 多路复用，可以用少量线程处理大量连接。

Redis 通常由单线程执行命令，避免了命令之间的锁竞争和频繁线程切换。Redis 6 开始可以使用线程处理部分网络 I/O，但命令执行仍以单线程为主。因此，一个耗时命令依旧可能阻塞后续请求，不能把“单线程”理解成所有工作都只有一个线程。

### Redis 单线程模型的优势与局限

单线程让单条命令天然具备原子性，也使执行顺序更容易理解。只要一个命令没有执行完，其他命令就不会插入它的执行过程。

代价是慢命令会阻塞整个实例。对大集合执行全量查询、删除大 Key、运行复杂 Lua 脚本，都会拉高其他请求的延迟。生产环境应限制单次操作的数据量，使用 `SCAN` 代替 `KEYS` 遍历，并优先采用异步删除命令处理大 Key。

## 2. 常用数据类型

### Redis 常用数据类型概览

| 类型 | 特点 | 常见场景 |
| --- | --- | --- |
| String | 字符串、整数或二进制数据 | 对象缓存、计数器、验证码、锁标识 |
| List | 有序且可重复，支持双端操作 | 最新列表、栈、简单队列 |
| Hash | 一个 Key 下保存多个字段 | 用户资料、购物车、对象字段更新 |
| Set | 无序去重集合，支持集合运算 | 点赞去重、共同关注、抽奖 |
| ZSet | 成员唯一，按 score 排序 | 排行榜、热度排序、延迟任务 |
| Bitmap | 对 String 进行位操作 | 签到、在线状态、活跃统计 |
| HyperLogLog | 近似统计基数 | 大规模 UV 估算 |
| Geo | 保存经纬度并按距离查询 | 附近门店、附近用户 |
| Stream | 支持消费组的持久化消息流 | 事件记录、轻量消息队列 |

选择类型时，应先看业务需要的操作，而不是把所有对象都序列化成 String。需要字段级更新时使用 Hash，需要去重和集合运算时使用 Set，需要排序和范围查询时使用 ZSet。

### String 的特点与使用场景

String 是最基础的 Key-Value 类型，值可以是文本、整数或二进制数据，单个值最大为 512MB，但实际使用不应接近这个上限。

常见命令包括 `SET`、`GET`、`MGET`、`INCR` 和 `INCRBY`。`INCR` 的原子自增适合阅读量和序列号；`SET key value EX 60 NX` 可以同时设置过期时间和“仅在不存在时写入”，常用于验证码和分布式锁的基础实现。

对象可以整体序列化为 JSON 存入 String，读写简单；如果经常只更新少数字段，则 Hash 通常更合适。

### List 的特点与使用场景

List 是有序且允许重复的字符串序列，支持从两端插入和弹出。`LPUSH`、`RPUSH`、`LPOP`、`RPOP` 可以组合出栈或队列，`LTRIM` 可以只保留固定数量的最新元素。

List 可以实现简单任务队列，但它缺少完善的消费组、消息确认和故障转移机制。需要可靠消费时，可以使用 Redis Stream；业务规模更大、可靠性要求更高时，应选择专用消息中间件。

### Hash 的特点与使用场景

Hash 在一个 Key 下保存多个 field-value，适合表示字段较少且需要局部更新的对象。例如购物车可以用用户 ID 作为 Key、商品 ID 作为 field、数量作为 value，再通过 `HINCRBY` 原子修改数量。

Hash 不适合无限增加字段。字段过多会形成大 Key，使迁移、删除和全量读取变慢。复杂嵌套结构也不适合直接展开成 Hash，此时应重新划分 Key 或使用文档数据库。

### Set 的特点与使用场景

Set 是无序去重集合，支持成员判断以及交、并、差集。点赞去重可以使用 `SADD`，共同关注可以使用 `SINTER`，随机抽取成员可以使用 `SRANDMEMBER` 或 `SPOP`。

集合运算会消耗与数据规模相关的 CPU 和内存。对大集合直接求交集可能阻塞实例，生产中应限制集合大小，或者把计算移到离线任务和专门的分析系统。

### ZSet 的特点与使用场景

ZSet 中的成员唯一，每个成员关联一个 score，并按照 score 排序。它适合排行榜、热搜和按时间排序的任务集合。`ZINCRBY` 可以更新分值，`ZRANGE`、`ZREVRANGE` 和 `ZRANGEBYSCORE` 可以按排名或分值范围读取数据。

用 ZSet 实现延迟任务时，通常把执行时间戳作为 score，再周期性查询已到期任务。不过 Redis 本身不会主动通知消费者，多个消费者还要解决重复领取和执行幂等问题。可靠性要求高的延迟任务更适合专门的消息系统。

### Bitmap、HyperLogLog 与 Geo 的适用场景

Bitmap 使用位表示布尔状态，适合用户 ID 较连续的签到和活跃统计。它占用空间与最大 offset 有关，如果用户 ID 极度稀疏，内存利用率会很差。

HyperLogLog 用固定大小的空间估算去重数量，标准误差约为 0.81%，适合 UV 等只关心近似值的场景。它不能返回具体成员，也不能提供精确计数。

Geo 基于经纬度保存位置并支持距离和范围查询，适合附近门店等基础地理场景。它不是完整的地理信息系统，复杂多边形、道路距离和轨迹分析应交给专业 GIS 系统。

### Stream 与 List 的消息队列能力对比

List 适合简单的先进先出队列，结构和命令较少。Stream 会为消息生成有序 ID，并支持消费组、ACK、Pending 列表和消息重新认领，更适合需要确认与重试的消费流程。

Stream 的可靠性仍依赖持久化、复制和消费端幂等。它适合规模可控、已经依赖 Redis 的轻量事件流；需要跨机房复制、复杂路由和长期消息堆积时，应使用专业消息中间件。

## 3. 底层数据结构

### SDS 相比 C 字符串的改进

SDS 会记录字符串长度，因此获取长度是 O(1)，不需要遍历到 `\0`。它按长度判断数据边界，可以安全保存二进制内容；同时通过预分配和惰性释放减少频繁的内存重新分配。

C 字符串仍可用于部分无需修改的常量，但 Redis 中需要频繁读写的字符串对象更适合 SDS。

### 渐进式 rehash 的工作方式

Redis 的字典扩容时不会一次迁移所有数据，而是同时保留旧、新两个哈希表，把迁移工作分散到后续的增删改查和定时任务中。这样可以避免大字典一次扩容长时间阻塞主线程。

rehash 期间查询可能需要检查两个哈希表，新写入通常进入新表。渐进迁移降低了单次延迟，但扩容期间会临时占用更多内存。

### listpack 与 intset 的内存优化

Redis 会根据元素数量、大小和类型选择更紧凑的内部编码。listpack 使用连续内存保存小型集合，减少指针开销；intset 使用有序整数数组保存元素全为整数的小型 Set。

数据超过配置阈值后，Redis 会转换为更适合大数据量的结构，例如哈希表或跳表。紧凑结构节省内存，但中间插入和更新的成本可能较高，因此编码会随数据规模变化。

### ZSet 的哈希表与跳表结构

ZSet 既要按成员快速查分，又要按 score 排序和范围遍历。哈希表提供成员到 score 的 O(1) 平均查询，跳表提供 O(log n) 平均查找以及高效的有序范围遍历。

小型 ZSet 可以使用 listpack 节省内存；达到阈值后才转换为哈希表和跳表的组合。两种结构服务于不同查询需求，并不是重复保存两份独立业务数据。

## 4. Key 与内存管理

### Redis Key 的设计原则

Key 应体现业务层级，例如 `user:profile:1001`，既方便识别，也能避免不同模块重名。名称不宜过长，否则会额外消耗内存；也不能过度缩写到难以排查。

缓存 Key 通常需要设置 TTL，并根据业务更新频率选择过期时间。批量 Key 应加入随机抖动，避免同一时刻集中失效。不要依赖 `KEYS` 在生产实例中搜索业务 Key，应使用明确命名、索引集合或渐进式 `SCAN`。

### Redis 的过期 Key 删除机制

Redis 结合惰性删除和定期删除。访问 Key 时发现已经过期，会立即删除；后台任务还会周期性抽样检查带 TTL 的 Key，删除其中已过期的数据。

这种方式能在 CPU 消耗和内存释放之间取平衡，但过期 Key 不一定在 TTL 到达的瞬间从内存消失。内存达到 `maxmemory` 后，Redis 还会根据配置的淘汰策略处理数据，例如从设置过期时间的 Key 或全部 Key 中按 LRU、LFU、随机等规则选择淘汰对象。

### 大 Key 与热 Key

大 Key 是值本身很大或集合成员过多的 Key，会增加网络传输、删除、持久化和集群迁移成本。热 Key 是访问量集中在少数 Key 上，可能把单个 Redis 节点或网络连接打满。

大 Key 应拆分数据、限制集合长度，并使用 `UNLINK` 等异步删除方式；热 Key 可以通过本地缓存、只读副本、请求合并或业务拆分分散压力。两类问题都应先通过监控和采样确认，不能只凭 Key 名判断。

# 二、缓存应用与并发控制

## 1. 缓存读写

### Cache Aside 的读写流程

Cache Aside 由业务代码同时维护缓存和数据库。读取时先查缓存，未命中再查数据库并回填；写入时先更新数据库，再删除缓存。

```text
读取：查缓存 → 未命中 → 查数据库 → 回填缓存
写入：更新数据库 → 删除缓存
```

删除而不是直接更新缓存，可以减少多个并发写操作互相覆盖的问题。Cache Aside 仍然只能提供最终一致性，数据库更新与缓存删除之间始终存在短暂窗口。

### 先更新数据库再删除缓存的原因

如果先删除缓存再更新数据库，并发读可能在数据库更新前读到旧值并重新写入缓存，最终形成长期脏数据。先更新数据库再删除缓存时，虽然仍可能出现竞态，但窗口通常更小，也更容易通过重试处理。

删除缓存失败会让旧数据继续存在，因此需要重试、消息队列或订阅 binlog 等方式补偿。对一致性特别敏感的读取，可以短时间走主库或直接绕过缓存，而不是试图让缓存参与强一致事务。

## 2. 缓存异常

### 缓存穿透、击穿与雪崩的区别

| 问题 | 原因 | 常见处理方式 |
| --- | --- | --- |
| 缓存穿透 | 持续查询根本不存在的数据 | 缓存空值、布隆过滤器、参数校验 |
| 缓存击穿 | 单个热点 Key 失效，大量请求同时回源 | 请求合并、互斥重建、逻辑过期 |
| 缓存雪崩 | 大量 Key 同时失效或 Redis 整体不可用 | TTL 随机抖动、多级缓存、限流降级 |

三者都可能把流量推向数据库，但触发范围不同。穿透针对不存在的数据，击穿针对单个热点，雪崩则是大面积失效。

### 使用布隆过滤器拦截缓存穿透

布隆过滤器使用多个哈希函数把元素映射到位数组。判断不存在时结果可靠；判断存在时可能误判，因为不同元素可能命中相同位置。

请求可以先经过布隆过滤器，明确不存在的 Key 直接拒绝，可能存在的 Key 再查询缓存和数据库。它适合数据集合相对稳定的场景；删除数据、过滤器重建和新增数据同步都需要单独设计。

### 热点 Key 的缓存击穿处理

一种方式是只允许一个请求获取互斥锁并重建缓存，其他请求等待或稍后重试。另一种方式是逻辑过期：Key 不立即删除，发现逻辑时间过期后由一个后台任务刷新，其他请求暂时返回旧值。

互斥重建能避免大量请求回源，但会增加等待；逻辑过期可保持低延迟，但业务必须接受短时间旧数据。选择取决于数据库承载能力和数据新鲜度要求。

### 缓存雪崩的防护措施

首先给 TTL 添加随机抖动，避免同批缓存同时到期。其次根据业务重要性准备本地缓存、限流、熔断和降级结果，防止 Redis 故障时所有请求直接压向数据库。

高可用 Redis 能降低单点故障概率，但故障切换仍有时间窗口，也不能解决错误配置、全量清理和流量突增。缓存不可用时的系统行为必须在应用层明确设计并演练。

## 3. 分布式锁

### Redis 分布式锁的正确加锁方式

加锁应使用一条原子命令，同时完成“仅在 Key 不存在时写入”和设置过期时间：

```text
SET lock:order:1001 <唯一标识> NX PX 30000
```

唯一标识用于区分锁的持有者，过期时间用于避免客户端崩溃后永久占锁。业务执行完成后，只有标识匹配的客户端才能删除锁。

锁只能减少并发执行，业务操作仍应具备幂等性。否则锁过期、网络延迟或故障切换仍可能造成重复处理。

### 使用 Lua 脚本原子释放锁

释放锁需要先判断锁值是否属于当前客户端，再执行删除。如果把 `GET` 和 `DEL` 分成两条命令，锁可能在两步之间过期并被其他客户端获取，此时原客户端会误删新锁。

Lua 脚本可以让判断和删除在 Redis 中原子执行：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

脚本本身也不应执行耗时逻辑，因为 Redis 会在脚本运行期间阻塞其他命令。

### 锁过期与看门狗续期

可以设置足够保守的过期时间，或者使用看门狗在确认客户端仍持有锁时周期性续期。续期动作也必须校验持有者，业务结束后要停止续期任务。

看门狗无法消除所有风险。长时间 GC 停顿、进程失联或网络分区仍可能让锁在业务结束前过期。对外部资源写入可以配合 fencing token，让资源端拒绝来自旧持有者的过期操作。

### Redis 分布式锁的适用场景与边界

Redis 锁适合性能优先、可以依靠幂等或补偿处理极少数重复执行的业务，例如定时任务防重、缓存重建和非关键资源竞争。

Redis 主从复制通常是异步的。主节点写入锁后如果立即故障，而锁尚未复制到新主节点，其他客户端可能再次加锁。Redlock 尝试在多个独立节点上取得多数锁，但仍依赖时间假设，并存在网络延迟和进程停顿等争议。资金等强一致场景更适合使用具备共识和租约机制的协调系统，并在资源端增加 fencing token。

## 4. 常见应用场景

### 计数、排行榜与限流

计数器可以使用 `INCR` 或 Hash 的 `HINCRBY` 原子累加；排行榜可以用 ZSet 保存成员和分值，再按排名范围查询；简单限流可以用计数器配合过期时间，或通过 Lua 脚本实现滑动窗口、令牌桶等逻辑。

原子命令只能保证 Redis 内部操作的一致性。如果计数结果还要写入数据库，应设计异步落库、去重和失败补偿。限流规则也应考虑多实例共享、时间精度和 Redis 故障时选择放行还是拒绝。

# 三、持久化、高可用与集群

## 1. 持久化

### RDB 与 AOF 的区别

RDB 定期生成某一时刻的数据快照，文件紧凑、恢复速度快，但故障时会丢失最近一次快照之后的数据。AOF 记录写命令，数据丢失窗口由刷盘策略决定，通常比 RDB 小，但文件更大，恢复过程也更复杂。

| 对比项 | RDB | AOF |
| --- | --- | --- |
| 记录内容 | 某一时刻的数据快照 | 写命令日志 |
| 恢复速度 | 较快 | 通常较慢 |
| 数据丢失窗口 | 两次快照之间 | 取决于刷盘策略 |
| 文件体积 | 较小 | 通常较大 |
| 主要用途 | 备份、快速恢复 | 提高数据持久性 |

两种方式可以同时开启。恢复时 Redis 会优先使用数据更完整的持久化文件，但持久化不能代替异地备份和恢复演练。

### RDB 快照与写时复制

Redis 执行后台快照时会 fork 子进程，由子进程把快照写入临时文件，完成后再原子替换旧文件。父子进程起初共享内存页，父进程修改数据时才通过写时复制产生新页面。

写时复制不代表快照期间不会增加内存。写流量越大，被复制的页面越多；大实例 fork 本身也可能产生延迟。因此需要预留内存并监控 fork 耗时，避免在资源紧张时频繁生成快照。

### AOF 的刷盘策略

`appendfsync always` 每次写命令都尝试刷盘，数据最安全但性能开销最大；`everysec` 通常每秒刷盘一次，在性能和持久性之间取平衡；`no` 把刷盘时机交给操作系统，性能较好但数据丢失窗口更难控制。

生产中常用 `everysec`，故障时理论上可能丢失约一秒的数据。实际选择应根据业务可接受的数据丢失量确定，而不是默认认为开启 AOF 就绝不会丢数据。

### AOF 重写与混合持久化

AOF 持续追加会越来越大。重写会根据当前内存数据生成一份等价但更紧凑的新文件，例如多次修改同一个 Key 最终只保留恢复当前值所需的内容。

混合持久化会在 AOF 重写文件的前半部分写入 RDB 格式的全量数据，后面追加重写期间产生的增量命令。它兼顾了 RDB 的恢复速度和 AOF 的数据完整性，但生成过程依然需要关注 fork、磁盘空间和 I/O 抖动。

## 2. 主从复制

### Redis 主从复制流程

从节点首次同步或无法继续增量复制时，会请求全量同步。主节点生成 RDB 并发送给从节点，同时把快照期间的新写命令放入缓冲区；从节点加载 RDB 后，再应用这些增量命令。

连接短暂中断后，如果复制偏移量仍在主节点的复制积压缓冲区中，可以执行部分重同步，只发送缺失命令。缓冲区无法覆盖断线期间的数据时，仍需重新全量同步。

主从复制提供数据副本和读扩展，不等于强一致。应用从副本读取还可能看到延迟数据。对读后立即可见有要求的请求，应读取主节点或采用业务级一致性方案。

## 3. Sentinel 高可用

### Sentinel 的作用

Sentinel 监控 Redis 主从节点，在主节点故障后选择一个合适的从节点提升为新主节点，再让其他从节点跟随新主节点，并向客户端提供新的主节点地址。

单个 Sentinel 可能因为网络问题误判节点。多个 Sentinel 会先形成对主节点客观下线的判断，再选举一个 Sentinel 执行故障转移。生产中通常至少部署三个彼此独立的 Sentinel 实例，避免单点并提高判断可靠性。

### 主观下线与客观下线

主观下线（SDOWN）表示某一个 Sentinel 在指定时间内无法收到节点的有效响应。客观下线（ODOWN）表示足够数量的 Sentinel 都认为主节点不可用，达到了配置的 quorum。

客观下线只用于判断主节点是否需要故障转移。真正执行选主还需要 Sentinel 之间完成 Leader 选举，并获得多数 Sentinel 的授权。合理配置 quorum 和部署位置，可以减少网络分区造成的误切换。

### Sentinel 故障转移的数据风险

由于复制是异步的，新主节点可能缺少旧主节点最后一部分写入。网络分区时，旧主节点如果仍接收客户端写入，而另一侧已经提升新主节点，还可能产生脑裂和更多数据丢失。

可以通过 `min-replicas-to-write` 和 `min-replicas-max-lag` 限制主节点在副本不足或延迟过高时继续写入，但这会牺牲可用性。客户端也必须支持发现新主节点并正确重连。

## 4. Redis Cluster

### Redis Cluster 的数据分片

Redis Cluster 把 Key 空间划分为 16384 个哈希槽，每个主节点负责一部分槽。Key 通过 `CRC16(key) % 16384` 计算所属槽，客户端根据槽与节点的映射把请求发送到正确节点。

集群扩缩容时迁移的是槽及其 Key，而不是重新改变所有 Key 的取模结果。每个主节点还可以配置从节点，在主节点故障后参与自动切换。

### MOVED 与 ASK 重定向

`MOVED` 表示某个槽已经由另一个节点负责，客户端应更新本地槽路由并把后续请求发往新节点。`ASK` 通常出现在槽迁移期间，只要求当前请求临时访问目标节点，不应永久修改槽映射。

支持 Cluster 的客户端会自动处理重定向。频繁出现重定向可能说明客户端路由缓存过旧、槽正在迁移或集群状态不稳定，需要继续检查集群拓扑。

### Cluster 的多 Key 操作限制

Redis Cluster 通常要求一条多 Key 命令中的所有 Key 位于同一个槽，否则会返回 `CROSSSLOT`。可以使用 Hash Tag，让花括号中的相同内容参与槽计算，例如 `{user:1001}:profile` 和 `{user:1001}:orders` 会落入同一个槽。

Hash Tag 虽能支持关联 Key 的原子操作，但使用过度会让大量 Key 集中到少数槽，造成数据倾斜。应只把确实需要一起操作的 Key 放在同一 Hash Tag 下。

## 5. 部署方案选择

### 主从、Sentinel 与 Cluster 的方案选择

单机 Redis 适合开发环境和允许短时中断的非核心数据；主从复制可以增加副本并分担读请求，但故障切换仍需外部处理；Sentinel 适合数据量能放进单机、需要自动故障转移的场景；Cluster 适合单机容量或吞吐已经不足，需要分片扩展的场景。

Cluster 并不是默认最佳方案。它增加了槽迁移、多 Key 限制、客户端兼容和运维复杂度。如果单机容量和吞吐仍有余量，Sentinel 往往更简单。无论选择哪种方案，都需要监控延迟、内存、复制状态和持久化，并定期验证备份恢复与故障切换。
