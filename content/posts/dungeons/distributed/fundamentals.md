# 一、分布式基础理论

## 1. CAP 原则

### 什么是 CAP 原则？

CAP 描述分布式系统的三个特性：一致性、可用性和分区容错性。

- **一致性（Consistency）**：所有节点对同一份数据的观察保持一致，读请求能够看到最新的成功写入。
- **可用性（Availability）**：每个发送到非故障节点的请求都能在有限时间内得到非错误响应，但不保证返回最新数据。
- **分区容错性（Partition Tolerance）**：节点之间出现网络中断或消息丢失时，系统仍能继续运行。

分布式系统无法彻底避免网络分区。CAP 真正讨论的是：分区已经发生时，系统要优先保证一致性还是可用性，而不是平时只能从三个特性中任选两个。

### CP 和 AP 应该如何选择？

CP 系统在无法确认数据一致时，会拒绝或阻塞部分请求；AP 系统会继续响应，但允许不同节点暂时返回不同结果，之后再让数据收敛。

选型取决于错误结果的代价。余额扣减、库存最终确认等场景通常更重视一致性；动态信息流、部分统计数据可以接受短暂不一致，更偏向可用性。同一个系统也可以针对不同业务采用不同策略，不必整体固定为 CP 或 AP。

## 2. BASE 理论

### 什么是 BASE 理论？

BASE 是面向高可用分布式系统的一种设计思路，允许数据短暂不一致，通过异步同步、重试和补偿使数据最终收敛。

- **基本可用（Basically Available）**：故障期间允许降低响应速度或关闭非核心功能，但核心服务仍能工作。
- **软状态（Soft State）**：数据可以在一段时间内处于同步中的中间状态。
- **最终一致性（Eventually Consistent）**：没有新写入且通信恢复后，各副本最终得到一致结果。

BASE 不是放弃一致性。系统仍要定义收敛条件、重试策略、幂等处理和异常补偿，否则“最终”没有可验证的时间和结果边界。

# 二、分布式事务

## 1. 方案选择

### 微服务场景下如何保证数据一致性？

微服务通常拥有独立数据库，本地事务无法覆盖跨服务操作。常见方案包括 XA、TCC、Saga、Seata AT，以及可靠消息最终一致性。

| 方案 | 一致性与特点 | 适用场景 |
| --- | --- | --- |
| XA / 2PC | 由协调者统一提交或回滚，锁持有时间长 | 强一致要求高、并发压力可控 |
| TCC | 业务实现 Try、Confirm、Cancel | 资金冻结、库存预占等可明确补偿的业务 |
| Saga | 长事务拆成多个本地事务，并为每步设计补偿 | 流程较长、允许中间状态 |
| Seata AT | 一阶段提交本地事务，失败时用 Undo Log 补偿 | 支持关系型数据库、希望降低业务侵入 |
| 可靠消息 | 本地事务与消息可靠关联，下游异步处理 | 允许短暂不一致、吞吐量要求较高 |

实际选型先看业务是否真的需要强一致，再看能否接受锁等待、业务改造和补偿复杂度。多数跨服务业务更适合最终一致性；只有错误结果无法接受时，才值得承担强一致方案的成本。

### 2PC 和 3PC 有什么区别？

2PC 分为准备和提交两个阶段。协调者先询问所有参与者能否提交，全部准备成功后再通知提交，否则回滚。它能协调多个资源，但准备阶段会持有锁；协调者故障或网络异常时，参与者可能长时间阻塞。

3PC 在 2PC 中加入预提交阶段和超时机制，试图降低参与者一直等待协调者的风险。不过它增加了通信轮次，也无法在网络分区下同时保证一致性和可用性，因此业务系统中远不如 2PC、TCC 或可靠消息常见。

## 2. Seata 事务模式

### Seata 的核心组件有哪些？

Seata 由 TC、TM 和 RM 协同管理全局事务。

| 组件 | 职责 |
| --- | --- |
| TC（Transaction Coordinator） | 维护全局事务和分支事务状态，协调提交或回滚 |
| TM（Transaction Manager） | 定义全局事务边界，向 TC 发起开启、提交或回滚请求 |
| RM（Resource Manager） | 管理业务资源，注册分支事务并执行提交或回滚 |

```text
TM 开启全局事务
       ↓
RM 执行并注册分支事务
       ↓
TM 提交或回滚全局事务
       ↓
TC 协调各 RM 完成最终操作
```

TC 负责协调，不直接替业务服务修改数据；具体资源操作仍由 RM 完成。

### Seata XA 模式如何工作？

XA 模式依赖数据库原生 XA 协议。第一阶段，各分支执行 SQL 并进入准备状态，但不真正提交，同时保留数据库锁和连接；第二阶段，TC 根据所有分支的结果统一通知提交或回滚。

XA 的优势是数据库负责事务回滚，能够提供较强的一致性和隔离能力，业务侵入较低。代价是资源持有时间长，容易阻塞并发请求，而且底层数据库必须支持 XA。它更适合一致性要求高、事务规模小且并发压力可控的场景。

### Seata AT 模式如何工作？

AT 模式会代理业务 SQL，在第一阶段记录修改前后的数据镜像，并把业务数据和 Undo Log 放在同一个本地事务中提交。全局事务成功时，第二阶段异步清理 Undo Log；失败时，根据前镜像生成补偿操作，并用后镜像检查数据是否被其他事务修改。

AT 能较早释放数据库本地锁，并通过全局锁控制写冲突，因此并发能力通常好于 XA。但分支事务已经本地提交，其他普通事务可能读到尚未全局确认的数据，默认不能提供 XA 级别的全局读隔离。

### Seata XA 和 AT 模式有什么区别？

| 对比维度 | XA 模式 | AT 模式 |
| --- | --- | --- |
| 实现基础 | 数据库 XA 协议 | SQL 代理、全局锁和 Undo Log |
| 第一阶段 | 执行但不提交 | 提交本地事务 |
| 第二阶段提交 | 提交数据库事务 | 清理 Undo Log |
| 第二阶段回滚 | 数据库原生回滚 | 根据 Undo Log 补偿 |
| 资源占用 | 长时间持有本地锁和连接 | 较早释放本地锁 |
| 隔离能力 | 较强 | 默认不提供全局读隔离 |
| 使用限制 | 数据库需要支持 XA | SQL 需要满足 AT 的解析和回滚要求 |

核心区别是第一阶段是否提交本地事务。XA 用资源占用换取更强隔离，AT 用补偿机制换取更高并发。

## 3. 可靠消息

### RocketMQ 事务消息如何保证最终一致性？

RocketMQ 事务消息把本地事务结果与消息是否可见关联起来，解决“数据库已经提交，但消息没有成功发送”的问题。

```text
发送半消息
    ↓
执行本地事务
    ↓
提交或回滚消息状态
    ↓ 状态未知
Broker 回查本地事务
    ↓
消息对消费者可见
```

生产者先发送消费者不可见的半消息，Broker 确认写入后再执行本地事务。事务成功则提交消息，失败则回滚；如果 Broker 没收到明确结果，会回查生产者保存的事务状态。

事务消息只保证本地事务与消息投递的一致性，不能保证消费者处理必然成功。消费者仍需实现幂等、重试、死信处理和人工补偿，才能让跨服务数据最终收敛。

# 三、微服务架构

## 1. 架构选择

### 微服务相比单体架构有什么优缺点？

微服务按照业务边界拆分应用，每个服务可以独立开发、部署和扩容。它能降低大型系统的模块耦合，让热点服务单独扩容，也便于不同团队并行迭代。

代价是调用从进程内方法变成网络通信，系统需要额外处理超时、重试、服务发现、链路追踪、配置管理和故障传播。跨服务事务与运维成本也会明显增加。

微服务不是系统成熟度的标志。业务简单、团队较小或边界尚未稳定时，模块化单体通常更容易维护；当业务边界明确，并且独立部署、扩容和团队自治带来的收益超过分布式成本时，再进行拆分更合适。

## 2. 服务发现

### 注册中心有什么作用？

注册中心维护服务名称与实例地址的映射，使调用方不需要写死 IP 和端口。服务实例启动后注册自身信息，并通过心跳或健康检查维持状态；实例上线、下线或故障后，注册中心更新可用列表并通知客户端。

注册中心通常只提供实例列表，不直接转发业务请求。客户端、网关或代理再根据轮询、随机、权重等策略选择实例。使用本地缓存可以在注册中心短暂不可用时继续调用已有实例，但也要处理缓存信息过期的问题。

## 3. 配置管理

### 配置中心如何实现动态刷新？

客户端启动时从配置中心拉取配置并建立监听。配置发生变化后，客户端收到通知或检测到版本变化，再拉取最新内容、更新本地缓存，并触发支持刷新的组件重新读取配置。

以 Nacos 为例，1.x 主要通过长轮询感知变化，2.x 开始使用长连接通信。Spring Cloud 应用可以结合配置绑定或 `@RefreshScope` 刷新 Bean，但不是所有对象都能无损热更新。数据库连接池、线程池和涉及资源生命周期的组件通常需要额外的更新与回滚逻辑。

动态配置上线前应校验格式、控制权限并保留历史版本。对于影响范围大的配置，还应采用灰度发布，避免一次错误修改同时影响所有实例。

# 四、服务治理

## 1. 服务保护

### Sentinel 如何保护服务？

Sentinel 通过限流、并发隔离和熔断降级限制故障影响范围。

- **限流**控制进入资源的请求速率，避免流量超过处理能力。
- **并发隔离**限制同时执行某个资源的线程数，防止慢调用耗尽共享线程。
- **熔断降级**在慢调用或异常达到阈值后暂时停止访问故障资源，让请求快速失败或进入兜底逻辑。

Sentinel 的线程数限制属于轻量级并发隔离，不等于为每个接口创建独立线程池。治理规则也不能替代容量规划，应结合压测结果设置阈值，并持续观察拒绝率和业务成功率。

### Sentinel 有哪些流量控制方式？

Sentinel 常见流控效果包括快速失败、Warm Up 和排队等待。

| 方式 | 行为 | 适用场景 |
| --- | --- | --- |
| 快速失败 | 超过阈值后立即拒绝 | 接口不能承担额外压力 |
| Warm Up | 逐步提高允许通过的 QPS | 冷启动或缓存尚未预热 |
| 排队等待 | 让请求按较稳定的间隔通过 | 削峰填谷、下游处理速率固定 |

规则还可以按 QPS、并发线程数或热点参数统计。热点参数限流是按商品 ID、用户 ID 等参数值单独控制流量，它是一种统计维度，不是与快速失败并列的流控效果。

## 2. 限流算法

### 常见限流算法有什么区别？

| 算法 | 工作方式 | 优点 | 局限 |
| --- | --- | --- | --- |
| 固定窗口 | 统计固定时间段内的请求数 | 实现简单、开销低 | 窗口边界可能出现瞬时双倍流量 |
| 滑动窗口 | 统计最近一段时间的多个小窗口 | 统计更平滑 | 需要维护更多状态 |
| 漏桶 | 请求进入队列后按固定速率流出 | 下游流量稳定 | 增加等待时间，突发过大时会丢弃 |
| 令牌桶 | 按固定速率生成令牌，请求先取令牌 | 控制平均速率并允许一定突发 | 桶容量过大时瞬时压力仍可能过高 |

需要精确限制时间范围内的请求数时可以使用滑动窗口；希望把流量平滑到固定速率时适合漏桶；既要限制长期速率又要容纳短时突发时，令牌桶更常见。

## 3. 熔断降级

### 熔断器有哪些状态？

熔断器通常有 Closed、Open 和 Half-Open 三个状态。

```text
Closed ──达到熔断条件──► Open
   ▲                       │
   │ 探测成功              │ 等待熔断时长
   │                       ▼
   └──────────────── Half-Open
                    探测失败 │
                             └──► Open
```

Closed 状态正常放行并统计慢调用和异常；达到阈值后进入 Open，请求直接失败；等待一段时间后进入 Half-Open，放行少量探测请求。探测成功则恢复 Closed，失败则重新 Open。

熔断的目的不是修复下游，而是阻止故障沿调用链扩散。业务还需要设置合理的调用超时，并为可降级请求准备明确的兜底结果。

# 五、一致性哈希

## 1. 数据映射

### 什么是一致性哈希？

一致性哈希用于在分布式缓存或存储节点之间分配数据，重点解决节点数量变化时大量 Key 重新映射的问题。普通的 `hash(key) % N` 在 N 改变后会让大部分映射失效，而一致性哈希只迁移环上相邻的一部分数据。

它把哈希空间首尾相连形成逻辑环，节点和 Key 都映射到环上。一个 Key 通常归属于从自身位置顺时针遇到的第一个节点。新增节点时，只接管它与前一个节点之间的区间；删除节点时，该区间的数据转移给下一个节点。

### 一致性哈希有哪些局限？

真实节点在哈希环上的位置未必均匀。节点较少时，某些节点可能负责很大的区间，导致数据量和请求量倾斜；单个节点退出后，它负责的全部负载还可能集中转移到相邻节点。

一致性哈希减少的是扩缩容时的迁移范围，并不天然保证负载均衡。热点 Key 也不会因为哈希环而自动分散，因为同一个 Key 仍然落在一个位置。

## 2. 虚拟节点

### 虚拟节点如何改善数据分布？

虚拟节点让一个真实节点在哈希环上拥有多个位置。数据先映射到某个虚拟节点，再通过映射关系找到真实节点。只要虚拟节点数量足够且哈希分布合理，每个真实节点负责的区间就会更分散，扩缩容时的负载转移也更平滑。

不同配置的机器还可以分配不同数量的虚拟节点，近似实现加权分配。不过虚拟节点会增加路由表和迁移管理成本，实际数量需要根据节点规模和负载分布验证，而不是越多越好。
