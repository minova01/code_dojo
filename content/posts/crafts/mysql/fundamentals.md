# 一、MySQL 基础与 SQL

## 1. MySQL 逻辑架构

### 一条 SQL 在 MySQL 中如何执行？


一条 SQL 大致会经过连接器、解析器、优化器和执行器，最后由存储引擎完成数据读写。连接器负责连接、认证和权限；解析器检查语法并生成语法树；优化器根据索引和统计信息选择执行计划；执行器再调用存储引擎接口。排查 SQL 问题时，也可以沿着连接、执行计划、I/O 和锁等待这条链路定位。

**展开理解：**

MySQL Server 层负责连接管理、SQL 解析、优化和执行，存储引擎层负责数据页、索引、事务和锁。InnoDB 是 MySQL 8.0 的默认存储引擎。

### SQL 可以分为哪些类型？


SQL 通常分成五类：DDL 定义结构，DML 修改数据，DQL 查询数据，DCL 管理权限，TCL 控制事务。日常开发最常用的是 `SELECT`、`INSERT`、`UPDATE`、`DELETE`，数据库变更会用到 `CREATE` 和 `ALTER`，多步写操作则用 `COMMIT`、`ROLLBACK` 控制事务。

| 类型 | 作用 | 常见语句 |
| --- | --- | --- |
| DDL | 定义数据库对象 | `CREATE`、`ALTER`、`DROP`、`TRUNCATE` |
| DML | 写入和修改数据 | `INSERT`、`UPDATE`、`DELETE` |
| DQL | 查询数据 | `SELECT` |
| DCL | 控制权限 | `GRANT`、`REVOKE` |
| TCL | 控制事务 | `COMMIT`、`ROLLBACK`、`SAVEPOINT` |

## 2. SELECT 执行顺序

### SELECT 的书写顺序和执行顺序有什么区别？


SQL 的书写顺序一般是 `SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT`，逻辑执行顺序则是 `FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`。因此，`WHERE` 通常不能使用 `SELECT` 中刚定义的别名，而 `ORDER BY` 可以；`WHERE` 不能过滤聚合结果，而 `HAVING` 可以。

```text
书写顺序：SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

### WHERE 和 HAVING 有什么区别？


`WHERE` 在分组前过滤原始行，`HAVING` 在分组后过滤聚合结果。能够提前判断的条件应优先写在 `WHERE`，因为它能减少后续分组的数据量。只有依赖 `COUNT`、`SUM` 等聚合结果的条件，才需要放到 `HAVING`。

```sql
SELECT city, COUNT(*) AS user_count
FROM users
WHERE status = 1
GROUP BY city
HAVING COUNT(*) > 100
ORDER BY user_count DESC;
```

## 3. JOIN、子查询与窗口函数

### INNER JOIN 和 LEFT JOIN 有什么区别？


`INNER JOIN` 只返回两张表都能匹配的行，`LEFT JOIN` 会保留左表全部数据，右表匹配不到时补 `NULL`。`LEFT JOIN` 中，右表过滤条件写在 `ON` 里不会丢掉左表数据；如果写进 `WHERE`，补出的 `NULL` 行会被过滤，结果可能接近 `INNER JOIN`。

```sql
SELECT u.id, u.name, d.name AS department_name
FROM users AS u
LEFT JOIN departments AS d
  ON u.department_id = d.id
 AND d.status = 1;
```

### IN、EXISTS 和 JOIN 应该如何选择？


`IN` 表示某个值是否属于子查询结果集合，`EXISTS` 只判断相关子查询能否找到一行，`JOIN` 则适合同时取得两边的数据。现代 MySQL 会对很多子查询进行半连接等优化，所以不能简单认为 `EXISTS` 一定比 `IN` 快。选择时先保证语义正确，再用 `EXPLAIN ANALYZE` 比较真实执行情况。

只需要判断关联数据是否存在时，`EXISTS` 的表达通常更直接：

```sql
SELECT u.id, u.name
FROM users AS u
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.user_id = u.id
    AND o.status = 1
);
```

### 窗口函数与 GROUP BY 有什么区别？


`GROUP BY` 会把多行聚合成一行，窗口函数会保留原始行，并在指定窗口内计算排名、累计值或前后行差异。分组 Top-N、连续排名和累计统计通常适合窗口函数；只需要每组汇总结果时使用 `GROUP BY`。

```sql
SELECT name,
       department_id,
       salary,
       ROW_NUMBER() OVER (
         PARTITION BY department_id
         ORDER BY salary DESC
       ) AS row_number
FROM employees;
```

常用窗口函数包括：

- `ROW_NUMBER()`：连续编号，不保留并列名次。
- `RANK()`：并列时占用后续名次。
- `DENSE_RANK()`：并列时不跳过后续名次。
- `LAG()`、`LEAD()`：读取前一行或后一行。
- `SUM() OVER (...)`：计算累计值或移动汇总。

## 4. 数据写入与修改

### INSERT、UPDATE 和 DELETE 使用时要注意什么？


`INSERT` 应明确列名，批量插入可以减少网络往返。执行 `UPDATE` 或 `DELETE` 前，要先用相同的 `WHERE` 条件确认影响范围，避免误操作整表。多条相关写操作必须一起成功或失败时，应显式开启事务；批量修改还要控制单次数据量，避免长事务和大范围锁定。

```sql
INSERT INTO users (name, email)
VALUES ('张三', 'zhangsan@example.com'),
       ('李四', 'lisi@example.com');

SELECT id, status FROM orders WHERE id = 1001;
UPDATE orders SET status = 2 WHERE id = 1001;
```

# 二、InnoDB 与数据存储

## 1. 数据页与缓存

### 为什么数据库性能通常受磁盘 I/O 影响？


数据库数据主要保存在磁盘上，而随机磁盘访问比内存访问慢得多。InnoDB 通过页读取、B+ 树索引和 Buffer Pool 减少磁盘 I/O。它通常以 16KB 页为基本读写单位，一次会加载整页，因此数据布局、索引层级和缓存命中率都会直接影响查询性能。

### Buffer Pool 有什么作用？


Buffer Pool 是 InnoDB 的内存缓存，用来保存数据页和索引页。查询命中缓存时不需要访问磁盘，修改也会先发生在内存页上，再由后台线程把脏页刷回磁盘。Buffer Pool 能显著降低 I/O，但脏页集中刷盘、可用页不足或缓存被大扫描污染时，也可能造成性能波动。

**展开理解：**

InnoDB 使用经过调整的 LRU 策略管理缓存页。新读取的页先进入较冷区域，只有再次访问后才进入热点区域，这样可以减少一次大型扫描把长期热点数据全部挤出的情况。

## 2. 日志与崩溃恢复

### WAL 和 redo log 如何保证崩溃安全？


WAL 的核心是先写日志，再写数据页。事务修改数据时，InnoDB 先顺序写 redo log，数据页可以稍后异步落盘；如果数据库崩溃，就通过 redo log 重放已经提交但尚未刷盘的修改。这样既把随机写转换成更高效的顺序写，也保证了事务的持久性。

### redo log、undo log 和 binlog 有什么区别？


redo log 记录页级物理修改，负责崩溃恢复；undo log 保存修改前的版本，负责事务回滚并支持 MVCC；binlog 属于 Server 层，记录逻辑变更，主要用于复制和数据恢复。redo log 与 binlog 是两套日志，MySQL 通过两阶段提交保证它们在事务提交时保持一致。

| 日志 | 所属层 | 主要用途 |
| --- | --- | --- |
| redo log | InnoDB | 崩溃恢复，保证已提交修改不会因数据页未落盘而丢失 |
| undo log | InnoDB | 事务回滚，并为 MVCC 提供历史版本 |
| binlog | MySQL Server | 复制、增量备份和时间点恢复 |

### MySQL 为什么需要两阶段提交？


两阶段提交是为了保证 redo log 和 binlog 的事务状态一致。提交时，redo log 先进入 prepare 状态，然后写 binlog，最后把 redo log 标记为 commit。发生崩溃时，MySQL 可以根据 redo log 状态和 binlog 是否完整决定提交或回滚，避免主库数据与复制日志不一致。

# 三、索引与 B+ 树

## 1. B+ 树结构

### 为什么 InnoDB 使用 B+ 树作为索引？


InnoDB 使用 B+ 树，主要是为了减少磁盘 I/O，并同时支持等值查询、范围查询和排序。B+ 树分叉多、树高低，查询通常只需要访问少量页面；数据集中在叶子节点，叶子节点又按顺序连接，所以范围扫描也很高效。哈希结构虽然适合等值查询，但不适合范围和排序，因此不适合作为通用索引。

常见的“三层 B+ 树可以存放千万级数据”只是估算。实际容量会受到主键长度、行大小、页利用率和索引类型影响。

### B+ 树和 B 树有什么区别？


B 树的非叶子节点也可以保存数据，B+ 树的数据集中在叶子节点，非叶子节点主要保存键和子节点指针。这样一个页面能容纳更多索引项，树高通常更低。B+ 树叶子节点还按顺序连接，更适合数据库常见的范围查询和顺序扫描。

## 2. InnoDB 索引类型

### 聚簇索引和二级索引有什么区别？


聚簇索引的叶子节点保存完整行数据，一张 InnoDB 表只有一份聚簇数据组织，通常由主键构成。二级索引叶子节点保存索引列和主键值，查询其他列时要根据主键回到聚簇索引取完整行，这叫回表。主键越长，所有二级索引保存的主键副本也越大。

### 什么是回表和覆盖索引？


通过二级索引找到主键后，再访问聚簇索引读取其他列，这个过程叫回表。如果查询需要的字段都能从同一个索引取得，就不需要回表，这叫覆盖索引。覆盖索引可以减少随机 I/O，但不能为了覆盖所有查询而无限增加索引列，否则会增加空间和写入成本。

```sql
CREATE INDEX idx_users_name_age ON users(name, age);

SELECT name, age
FROM users
WHERE name = '张三';
```

### 联合索引的最左前缀原则是什么？


联合索引 `(a, b, c)` 先按 `a` 排序，`a` 相同时按 `b` 排序，再按 `c` 排序。因此查询从最左列开始连续匹配时，才能有效缩小扫描范围；跳过 `a` 直接查询 `b`，通常无法用这棵树快速定位。范围条件之后的列一般不能继续缩小索引区间，但仍可能通过索引条件下推参与过滤。

```text
a = ?                         可以定位
a = ? AND b = ?               可以继续定位
a = ? AND b = ? AND c = ?     可以继续定位
b = ? AND c = ?               无法直接利用最左列定位
```

## 3. 索引使用与设计

### 哪些写法容易导致索引无法有效使用？


常见情况包括跳过联合索引最左列、对索引列使用函数或运算、发生隐式类型转换、使用前导模糊匹配，以及查询命中表中大部分数据。`OR` 连接缺少索引的条件也可能让优化器放弃索引。最终是否使用索引要看执行计划，不能只根据规则判断。

```sql
-- 不利于普通索引定位
SELECT * FROM orders
WHERE DATE(created_at) = '2026-10-27';

-- 改为范围条件
SELECT * FROM orders
WHERE created_at >= '2026-10-27 00:00:00'
  AND created_at <  '2026-10-28 00:00:00';
```

### 索引越多越好吗？


索引不是越多越好。索引会占用磁盘和 Buffer Pool，每次插入、删除或修改索引列时也要维护对应的 B+ 树，因此会降低写入性能。索引应围绕真实的高频查询设计，低选择性字段、频繁变更字段和大文本字段通常不适合随意建立普通索引。

### 为什么常推荐自增主键？


自增主键大致按顺序写入，插入位置集中在 B+ 树末端，页分裂较少，缓存局部性也更好。随机 UUID 可能分散写入位置，增加页分裂和索引体积。不过主键选择还要考虑分布式唯一性、业务暴露和数据迁移，不能只看写入性能。

# 四、事务、MVCC 与锁

## 1. 事务与隔离级别

### ACID 分别表示什么？


ACID 分别是原子性、一致性、隔离性和持久性。原子性保证事务全部成功或全部回滚，主要依赖 undo log；隔离性控制并发事务之间的影响，依赖 MVCC 和锁；持久性保证提交后故障恢复仍能找回数据，主要依赖 redo log。一致性是最终目标，还需要数据库约束和业务逻辑共同保证。

| 特性 | 含义 | InnoDB 中的主要支撑机制 |
| --- | --- | --- |
| 原子性 Atomicity | 全部成功或全部回滚 | undo log |
| 一致性 Consistency | 事务前后满足数据和业务规则 | 数据库机制与应用逻辑 |
| 隔离性 Isolation | 控制并发事务之间的影响 | MVCC 与锁 |
| 持久性 Durability | 提交后可以从故障中恢复 | redo log 与刷盘策略 |

### 事务应该怎样使用？


多条写操作必须一起成功或失败时，应显式开启事务，成功后 `COMMIT`，异常时 `ROLLBACK`。事务要尽量短，不要在事务中执行 RPC、用户交互或长时间计算。MySQL 默认开启自动提交，DDL 通常还会触发隐式提交，因此不能把 DDL 当作普通 DML 一样回滚。

```sql
START TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

### 并发事务会产生哪些问题？


并发事务常见问题有脏读、不可重复读和幻读。脏读是读到其他事务未提交的数据；不可重复读是同一事务两次读取同一行，值发生变化；幻读是同一事务两次执行范围查询，结果集合发生变化。不可重复读主要关注已有行被修改，幻读主要关注范围内出现或消失了符合条件的行。

### 四种事务隔离级别有什么区别？


四种隔离级别从低到高是读未提交、读已提交、可重复读和串行化。隔离越高，能避免的并发异常越多，但锁等待和并发成本也可能越高。InnoDB 默认使用可重复读，并通过 MVCC、记录锁和 next-key lock 处理常见的一致性问题。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 避免 | 可能 | 可能 |
| 可重复读 | 避免 | 避免 | InnoDB 处理常见场景 |
| 串行化 | 避免 | 避免 | 避免 |

## 2. MVCC 与 Read View

### MVCC 是什么，它如何工作？


MVCC 是多版本并发控制，目标是让普通读和写尽量不互相阻塞。InnoDB 通过事务 ID、回滚指针和 undo log 维护行的历史版本，再用 Read View 判断哪些版本对当前事务可见。查询会沿版本链找到可见数据，因此能够在不加读锁的情况下获得一致性快照。

### RC 和 RR 在 MVCC 中有什么区别？


RC 通常在每条一致性读语句开始时创建新的 Read View，所以能看到其他事务后来提交的数据。RR 通常在事务第一次一致性读时创建 Read View，并在事务中复用，因此多次读取能保持同一视图。可以简单记成：RC 每次读都刷新视角，RR 在事务内复用视角。

### 快照读和当前读有什么区别？


普通 `SELECT` 通常是快照读，它根据 Read View 读取可见的历史版本，不主动加行锁。`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 和 `SELECT ... FOR SHARE` 需要读取最新版本并加锁，属于当前读。MVCC 主要解决快照读，并不代表所有查询都不会加锁。

## 3. 锁与死锁

### 记录锁、间隙锁和 next-key lock 有什么区别？


记录锁锁定具体索引记录，间隙锁锁定两个索引记录之间的范围，next-key lock 是记录锁与前方间隙锁的组合。InnoDB 在可重复读下使用 next-key lock，可以阻止其他事务在锁定范围中插入新记录，从而控制当前读场景中的幻读。实际锁定范围取决于索引、查询条件和隔离级别。

### 为什么没有索引会扩大锁范围？


InnoDB 的行锁实际加在索引记录上。更新条件没有合适索引时，数据库需要扫描更多记录，并对扫描过程中符合锁定规则的记录或范围加锁，所以锁范围和等待概率都会增加。给更新条件建立合适索引，既能减少扫描，也能降低锁冲突。

### 什么是死锁，应该怎样处理？


死锁是多个事务各自持有对方需要的锁，形成循环等待。InnoDB 检测到死锁后会回滚其中一个事务，让其他事务继续执行。工程上应统一资源访问顺序、缩短事务、让更新命中索引，并在应用层对满足幂等条件的事务进行有限次数重试。

# 五、SQL 分析与慢查询优化

## 1. 定位慢查询

### 一条 SQL 很慢，应该怎样排查？


我会先通过监控或慢查询日志定位具体 SQL，再用 `EXPLAIN` 查看索引、连接顺序和估算扫描量，然后用 `EXPLAIN ANALYZE` 对比真实行数和耗时。接着判断瓶颈来自全表扫描、回表、排序、临时表、锁等待还是返回数据过多。优化后要在接近生产的数据量上实测，并且每次只改变一个主要因素。

```text
发现 SQL → 查看执行计划 → 确认真实瓶颈 → 针对性修改 → 对比验证
```

### 慢查询日志有什么作用？


慢查询日志用于记录执行时间超过阈值的 SQL，是定位线上慢语句的入口。日志可以用 `mysqldumpslow` 或 `pt-query-digest` 聚合，不能只看单次最慢语句，还要优先处理总耗时高、调用频繁的查询。生产环境的开关和阈值应通过配置或管理平台统一设置。

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
```

## 2. 执行计划

### EXPLAIN 中应该重点看哪些字段？


我会重点看 `type`、`key`、`rows` 和 `Extra`。`type` 表示访问方式，`key` 是实际使用的索引，`rows` 是估算扫描行数；`Extra` 可以看到覆盖索引、额外排序、临时表和 join buffer 等信息。还要注意 `rows` 只是估算，最终应结合 `EXPLAIN ANALYZE` 的实际数据判断。

| 字段 | 关注点 |
| --- | --- |
| `type` | 访问方式，例如 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL` |
| `possible_keys` | 可能使用的索引 |
| `key` | 实际选择的索引，`NULL` 表示未使用索引 |
| `key_len` | 实际使用的索引长度 |
| `rows` | 估算检查行数 |
| `filtered` | 条件过滤后预计保留的比例 |
| `Extra` | 覆盖索引、排序、临时表等补充信息 |

### Extra 中常见信息如何理解？


`Using index` 表示覆盖索引，`Using index condition` 表示索引条件下推；`Using filesort` 表示需要额外排序，`Using temporary` 表示使用临时表，`Using join buffer` 通常说明连接没有有效利用被驱动表索引。后面三项需要关注，但不能看到就直接判定有问题，还要结合数据量和实际耗时。

### EXPLAIN 和 EXPLAIN ANALYZE 有什么区别？


`EXPLAIN` 展示优化器估算的执行计划，不会真正执行普通查询；`EXPLAIN ANALYZE` 会实际执行 SQL，并显示真实耗时、循环次数和返回行数。两者结合可以发现统计信息估算偏差。因为 `EXPLAIN ANALYZE` 会执行语句，所以不能对高成本或有副作用的操作随意使用。

### 为什么优化器没有选择预期索引？


优化器选择的是估算成本最低的计划，而不是“有索引就一定用”。如果查询返回比例很高，二级索引带来的大量回表可能比全表扫描更贵；小表、统计信息过期、隐式转换或错误的联合索引顺序也会影响选择。可以先更新统计信息，再结合 `OPTIMIZER_TRACE` 查看优化器的成本判断，不应一开始就使用 `FORCE INDEX`。

## 3. 常见优化方法

### 如何减少 SQL 读取的数据量？


首先只查询业务需要的列，避免无条件 `SELECT *`；其次尽早过滤无关数据，并控制返回行数。深分页不要一直使用很大的 offset，能够使用稳定排序键时，优先采用游标分页。减少读取量通常比单纯调整参数更有效。

```sql
SELECT id, status, created_at
FROM orders
WHERE id > 100000
ORDER BY id
LIMIT 20;
```

### 如何为过滤、连接和排序设计联合索引？


联合索引要围绕具体查询设计，通常先考虑稳定的等值过滤列，再考虑范围或排序列，同时满足最左前缀。连接字段也要有合适索引，避免被驱动表反复全表扫描。索引列顺序不能只靠口诀决定，还要结合选择性、查询频率和执行计划验证。

```sql
SELECT id, user_id, status, created_at
FROM orders
WHERE user_id = 1001
  AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

这类查询可以评估联合索引 `(user_id, status, created_at)`。

### 如何优化排序、分组和去重？


排序、分组和去重的共同问题是处理的数据量可能很大。应先用 `WHERE` 尽量过滤，再检查联合索引能否同时满足过滤和排序。`Using filesort` 和 `Using temporary` 不是必须消除，但如果参与行数很多，就要考虑索引、查询改写或预聚合。

### 为什么要缩短事务和拆分大批量任务？


长事务会长期持有锁、积累 undo log，也会增加主从复制和故障恢复压力。事务中不应包含 RPC、用户交互或耗时计算。大批量更新可以在业务允许的前提下分批提交，但要明确分批后是否仍满足原来的原子性要求。

### 优化完成后如何验证？


优化不能只看 `EXPLAIN`，还要比较真实响应时间、扫描行数和资源消耗。我会在接近生产的数据分布上对比 P50、P95、P99，同时观察 CPU、I/O、锁等待和写入性能。每次只改一个主要因素，上线时灰度并保留回滚方案。

## 4. 数据架构边界

### 什么时候需要考虑缓存、搜索系统或分库分表？


当 SQL 和索引已经合理，但单表容量、写入吞吐或分析需求仍超过单实例能力时，才考虑架构调整。读多写少且允许短暂过期的数据可以使用缓存，全文检索交给搜索系统，大规模聚合交给分析型数据库；分区和分库分表应放在明确容量瓶颈之后。因为这些方案都会引入一致性、跨分片查询和运维复杂度，不能用来掩盖基础 SQL 问题。

# 六、主从复制与高可用

## 1. 复制原理

### MySQL 主从复制如何工作？


主库提交事务后把变更写入 binlog，从库的 I/O 线程接收 binlog 并写入 relay log，回放线程再执行 relay log 中的变更。复制可以提供数据副本，并让部分读取转移到从库，但它默认不是实时强一致。生产中还要关注 GTID、并行回放、复制过滤和数据校验。

```text
主库写 binlog
    ↓
从库 I/O 线程写 relay log
    ↓
从库回放线程应用变更
```

### binlog 有哪些格式？


binlog 主要有 `STATEMENT`、`ROW` 和 `MIXED` 三种格式。`STATEMENT` 记录 SQL，日志可能较小，但非确定性语句可能造成不一致；`ROW` 记录行变更，可靠性更高但日志量可能更大；`MIXED` 会根据语句选择方式。MySQL 8.0 通常使用 `ROW`。

### 异步复制和半同步复制有什么区别？


异步复制中，主库提交后不等待从库确认，写入延迟较低，但主库突然故障时可能丢失尚未传输的日志。半同步复制会等待至少一个从库确认收到日志，再向客户端返回，因此能缩小数据丢失窗口，但会增加提交延迟，超时后还可能退化为异步。半同步只确认日志到达，不代表从库已经回放完成。

## 2. 延迟与一致性

### 主从延迟通常由什么引起？


主从延迟的本质是主库生成日志的速度超过从库接收或回放速度。常见原因包括大事务、从库资源不足、锁等待、额外查询压力、表缺少合适主键，以及并行复制配置不合理。排查时要同时观察 relay log 堆积、回放线程状态和 GTID 位点，不能只看一个延迟秒数。

### 如何缓解主从延迟？


可以拆分大事务、启用并合理配置并行复制、保证表有合适主键、提升从库资源，并减少从库上的慢查询和额外负载。对延迟特别敏感的读取应走主库，不能只靠调整复制参数解决业务一致性问题。

### 读写分离会产生什么一致性问题？


写入主库后立即读取从库，可能因为复制延迟读到旧数据，也就是写后读不一致。强一致请求可以继续读取主库，或者等从库复制位点追上后再读取；允许短暂延迟的列表、统计和历史查询更适合从库。是否允许读旧数据必须由业务定义，不能只在数据库中配置读写分离。

## 3. 高可用

### 主从复制和高可用有什么区别？


主从复制负责把数据同步到副本，高可用负责主库故障后的检测、选主、切换和连接恢复。只有副本但没有自动或可控的故障转移，主库宕机后业务仍然会中断。完整方案还要处理误切换、脑裂、数据丢失窗口和旧主库恢复问题。

### 常见的 MySQL 高可用方案有哪些？


常见方案有 MHA、Orchestrator、MySQL Group Replication 和 InnoDB Cluster。MHA 与 Orchestrator 属于外部拓扑管理或故障转移工具；Group Replication 是 MySQL 内置组复制；InnoDB Cluster 在组复制基础上整合 Router 和管理工具。选择方案时要比较一致性、切换时间、运维能力和现有架构，而不是只看是否支持自动切换。

| 方案 | 特点 |
| --- | --- |
| MHA | 传统外部故障转移工具，通过脚本完成主库切换 |
| Orchestrator | 识别复制拓扑并协助或自动完成故障转移 |
| MySQL Group Replication | MySQL 内置组复制，可构建单主或多主组 |
| InnoDB Cluster | 组合 Group Replication、MySQL Router 与管理工具 |

### 高可用方案上线后还需要做什么？


高可用上线后还要定期做故障切换演练，并监控复制状态、数据一致性和切换耗时。应用侧要确认连接池、DNS 或 Router 能及时切到新主库，还要明确旧主库重新加入集群前的数据处理流程。没有演练过的自动切换，在真实故障时并不可靠。
