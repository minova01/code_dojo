# 一、Agent Loop 与任务执行

## 1. Claude Code 的基本组成

### 模型与 Agent Harness 的职责边界

Claude Code 不是一个只负责生成文本的模型，而是由 Claude 模型和外围运行环境共同组成的智能体系统。官方文档把这个外围运行环境称为 **Agent Harness**。

模型负责理解目标、分析当前信息并决定下一步行动；Agent Harness 负责向模型提供工具、管理上下文、执行工具调用、返回执行结果以及处理权限。模型提出“读取文件”或“运行测试”，真正访问文件系统和执行命令的是 Agent Harness。

这一区分可以概括为：

> 模型负责推理和决策，Agent Harness 负责执行和控制。

### Agent Loop 的三个阶段

Claude Code 官方将 Agent Loop 概括为三个不断交替的阶段：收集上下文、采取行动、验证结果。三个阶段不是严格的一次性流水线，复杂任务会在它们之间多次循环。

![Claude Code Agent Loop](../../../../diagrams/claude-code/agent-loop.drawio.svg)

例如，修复登录接口时，Claude Code 可能先搜索入口代码，再读取认证逻辑；发现问题后修改文件，并通过测试或静态检查验证结果。如果验证失败，工具返回的新信息会进入下一轮上下文，模型据此继续定位和修正。

每次工具执行都会产生新的事实。模型不是预先生成一份完整计划后机械执行，而是根据上一轮结果动态调整后续动作。

## 2. 工具调用与循环终止

### 工具让模型具备行动能力

没有工具时，模型只能返回文本。Claude Code 为模型提供文件读取、搜索、编辑、命令执行和外部服务访问等能力。一次典型工具调用包括以下过程：

1. 模型根据当前上下文生成工具调用请求。
2. Agent Harness 检查工具参数和权限。
3. 对应工具在本地或外部环境中执行。
4. 执行结果作为新的上下文返回模型。
5. 模型判断继续调用工具还是给出最终结果。

工具结果可能是文件内容、命令输出、错误信息或修改结果。即使工具执行失败，失败原因本身也是下一轮推理所需的信息，因此一次失败不一定意味着整个任务终止。

### 多个工具调用的执行关系

模型可以在一次响应中提出多个工具调用。彼此独立的读取、搜索或查询适合并行处理；存在数据依赖或会修改同一状态的操作则应按顺序执行。

是否能够并行不能只看工具名称，还要看调用之间是否共享输入和副作用。例如，同时搜索两个独立目录通常安全，而“修改配置文件”和“立即根据新配置执行构建”具有先后依赖，不能并行。

### Agent Loop 的结束条件

当模型不再请求工具并返回最终内容时，本轮 Agent Loop 通常结束。用户也可以随时中断执行并补充要求或调整方向。

工程上还需要通过权限、上下文容量、使用额度和错误处理限制约束循环。它们共同防止任务在重复失败、无效搜索或持续调用工具时无限运行。具体阈值会随版本、模型和用户配置变化，不宜写成固定数值。

## 3. 会话状态与结果输出

### 会话记录为后续操作提供连续性

Claude Code 会在本地保存会话中的消息、工具调用和工具结果，使会话能够恢复、回退或分支。恢复会话会在原有会话记录后继续追加内容；分支会复制已有历史并使用新的会话标识继续工作。

会话记录和模型上下文并不完全相同。前者是保存在本地的完整过程，后者是某一次模型调用实际能够看到的信息。随着任务持续进行，运行环境需要从会话记录中选择、压缩和组织本轮上下文。

### 流式输出改善长任务反馈

Claude Code 可以在模型生成内容和工具执行期间持续返回状态，而不必等到整个任务结束后一次性输出。这种方式不能缩短所有操作的实际耗时，但可以让用户及时看到当前进度，并在方向不正确时尽早中断。

# 二、上下文管理与提示缓存

## 1. 上下文的组成

### 上下文决定模型当前能够理解什么

模型不会自动记住此前发生的事情。每次调用都必须重新携带完成当前任务所需的信息。Claude Code 的上下文通常包含系统指令、项目规则、用户消息、模型回复、文件内容、工具调用结果、已加载的 Skill，以及运行环境注入的其他信息。

这些内容共同竞争有限的上下文窗口。文件读取越多、命令输出越长、任务轮次越多，可供后续推理使用的空间就越少。`/context` 可以帮助观察当前上下文由哪些内容构成。

### 持久规则不应只写在对话中

Claude Code 接近上下文上限时会压缩较早的对话。压缩会尽量保留用户目标和关键代码，但早期的细节指令仍可能丢失。

需要在整个项目中持续生效的约束应写入 `CLAUDE.md` 或相应规则文件，而不是只在会话开头说明一次。临时任务背景和当前进度适合保留在对话中，长期规范则应由项目文件承载。

## 2. 上下文压缩

### 压缩用于延长长任务的连续性

当上下文接近容量限制时，Claude Code 会自动将较早的会话压缩为摘要，也可以由用户通过 `/compact` 主动触发。压缩后的摘要会保留任务目标、重要决策和关键代码信息，并替代大量早期消息继续参与后续推理。

![上下文压缩与恢复流程](../../../../diagrams/claude-code/context-compaction.drawio.svg)

压缩并不是无损存储。摘要能降低 Token 占用，却可能遗漏早期约束或具体实现细节。官方文档因此建议把长期规则放进 `CLAUDE.md`，并允许通过 Compact Instructions 或 `/compact` 的附加说明指定需要优先保留的内容。

### 减少上下文占用的常用方法

压缩不是唯一手段。在达到压缩阈值之前，还可以通过以下方式降低上下文增长速度：

- 避免无目标地读取大量文件，只加载解决当前问题需要的内容。
- 对日志、构建输出和搜索结果先过滤，再把关键片段交给模型。
- 把高输出量且相对独立的调查任务交给子代理，仅返回结论。
- 将重复使用的操作流程放进 Skill，只有需要时才加载完整正文。
- 在任务阶段发生明显变化时，新建会话并提供清晰交接，而不是无限延长旧会话。

这些方式的共同目标不是单纯缩短文本，而是提高上下文中的有效信息密度。

## 3. 提示缓存

### 提示缓存复用稳定的前缀

Agent Loop 的相邻两次模型调用通常包含大量相同内容，例如工具定义、系统指令和此前的消息历史。如果每次都重新处理完整输入，会增加延迟和 Token 成本。

Anthropic 的提示缓存会复用请求中相同的提示前缀。随着多轮对话增长，缓存位置可以向后移动，使前面保持不变的内容被读取复用，而只处理新增的消息和工具结果。

### 稳定前缀能够提高缓存命中率

缓存依赖前缀匹配。较早位置发生变化时，后面的缓存内容也可能无法继续复用。因此，稳定的工具定义和系统指令应尽量放在前面，频繁变化的上下文放在后面。

工具列表变化也会影响缓存。如果系统启动时加载大量暂时用不到的工具，不仅占用上下文，还可能因为工具配置变动破坏稳定前缀。按需发现和加载工具有助于同时控制上下文体积和缓存成本。

提示缓存解决的是重复计算问题，上下文压缩解决的是容量问题。两者目标不同：缓存不会让上下文变短，压缩也不保证保留原始前缀。实际系统需要在上下文质量、容量、延迟和成本之间取得平衡。

# 三、Skill 与子代理

## 1. Skill 的定位

### Skill 是按需加载的任务说明

Skill 是包含指令和可选辅助资源的目录，核心入口为 `SKILL.md`。它适合保存需要反复使用的检查清单、操作流程和领域知识。

Skill 不是独立运行的程序，也不等同于子代理。Skill 主要回答“这一类任务应该怎样完成”，真正的推理和工具调用仍由模型及 Agent Harness 完成。

与把所有流程写入 `CLAUDE.md` 相比，Skill 的正文只有在使用时才进入上下文。Claude Code 可以根据描述自动选择 Skill，用户也可以通过 `/skill-name` 显式调用。

## 2. Skill 的发现与加载

### 渐进加载控制上下文成本

Claude Code 启动时会加载 Skill 的名称和描述，用于判断它们是否与当前任务相关；完整正文通常在 Skill 被调用后才加载。这种渐进加载方式让系统能够保留较大的能力目录，而不必始终承担所有说明正文的 Token 成本。

Skill 的描述既要说明它能做什么，也要说明什么时候应当使用。描述过于宽泛会造成误触发，描述过于模糊则可能导致模型无法发现它。

### Skill 支持显式调用和自动选择

用户通过斜杠命令调用 Skill 时，意图已经明确，Claude Code 会展开对应内容并传入参数。自动选择则由模型根据 Skill 描述和当前任务判断，因此属于语义匹配，不是确定性的路由规则。

Skill 可以使用 `$ARGUMENTS` 接收全部参数，也可以使用 `$ARGUMENTS[N]`、`$N` 或命名参数读取特定位置。参数会在 Skill 正文进入模型上下文前完成替换。

```yaml
---
name: code-review
description: 检查指定文件的代码质量与异常处理
---

请审查以下文件：

$ARGUMENTS
```

执行 `/code-review auth.go` 后，模型收到的任务说明中会包含 `auth.go`。

## 3. Skill 与子代理的配合

### 主上下文执行与隔离执行

普通 Skill 会把任务说明加载到当前会话，由主代理继续执行。它能够直接利用已有对话背景，但 Skill 内容及后续工具结果也会占用主上下文。

在 Skill 的 frontmatter 中设置 `context: fork` 后，Claude Code 会启动独立子代理，并把 Skill 正文作为任务提示。这个子代理拥有独立上下文，不会自动看到主会话历史，因此 Skill 必须包含完成任务所需的目标、输入和约束。

| 方式 | 上下文 | 适合场景 | 主要限制 |
| --- | --- | --- | --- |
| 主会话执行 | 共享当前会话上下文 | 依赖既有讨论和当前修改状态 | 工具结果会继续占用主上下文 |
| `context: fork` | 使用独立子代理上下文 | 调研、审查和高输出量任务 | 不能默认读取主会话历史 |
| 自定义子代理 | 独立系统提示、工具和权限 | 长期复用的专业角色 | 需要单独维护代理配置 |

这里的 `context: fork` 并不等于复制整个主会话。官方文档明确说明，它会把 Skill 内容交给新的子代理，而不是把此前全部对话一并传入。

### 子代理能够隔离高输出量任务

子代理适合处理会产生大量搜索结果、日志或文件内容的支线任务。它在自己的上下文中完成调查，只把摘要或结果交还主会话，从而避免大量中间材料占满主上下文。

这种隔离也有成本：子代理会产生独立模型请求，并且缺少主会话中没有显式提供的信息。简单任务直接在主会话完成通常更高效；只有当任务相对独立、输出量较大或确实需要不同权限和工具时，才值得使用子代理。

## 4. 使用原则

### Claude Code 机制的整体关系

Claude Code 的核心不是某一个单独功能，而是几套机制共同协作：Agent Loop 负责持续推进任务，上下文管理负责控制模型当前看到的信息，提示缓存降低重复输入的处理成本，Skill 固化可复用流程，子代理隔离独立且高输出量的工作。

设计或使用类似系统时，可以遵循以下原则：

1. 把稳定规则放在项目级指令中，把可复用流程放进 Skill。
2. 只向模型提供当前决策需要的信息，避免无差别堆积上下文。
3. 把工具结果当作下一轮推理输入，而不是只判断成功或失败。
4. 对独立且高输出量的任务使用子代理，对简单任务保持直接执行。
5. 对版本相关的阈值和内部实现保持谨慎，以官方文档和当前版本为准。
